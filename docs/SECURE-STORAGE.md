# Phase 07A — encrypted voucher vault foundation
- Versioned, bounded local vault, AES-256-GCM with randomized 96-bit IV and 128-bit authentication tag, AndroidKeyStore key, private noBackupFilesDir, AtomicFile replacement with read-back verification. No new dependency or permission. Do not recreate keys or overwrite ciphertext when decryption fails. No raw credentials in result strings or logs.
- Explicit UUID profile association; gateway address alone does not identify a network. Android network handles are transient and must not be persisted. Profile creation, identity checks, user consent and confirmed-login integration are not implemented in this change.
- Maximum 20 records initially, no silent eviction, profile-scoped list and deletion, no automatic saving, replay or migration. Record validation reuses login input policy. The vault is not invoked by the UI yet.
- 17 JVM tests using in-memory backend and JCA test keys. These do not validate AndroidKeyStore or Android AtomicFile behavior on real devices. API 24 unchanged.
- Key protection depends on device implementation; hardware-backed keys are not guaranteed, no biometric or user-auth binding yet. App process access, rooted/compromised devices, memory strings, ciphertext rollback and forensic deletion remain limitations. No backup or cloud sync. No automatic reset on lost key.
- Next 07B: explicit profile management and save consent only after matching session evidence, with separate treatment of unverified HTTP; 07C: masked saved cards, explicit selection/deletion and no automatic login. Reassess bounds and data-store choice if scope grows.
- References: https://developer.android.com/privacy-and-security/keystore and https://developer.android.com/reference/android/util/AtomicFile

## Phase 07B1 — explicit network profiles and confirmed-save policy
- Encrypted vault document v2 includes up to 20 manually named profiles, each UUID and gateway. Existing v1 ciphertext remains readable; its records are not silently assigned to new profiles. Same gateway may have multiple explicitly selected profiles. Profile name is a label, not authenticated SSID/BSSID or proof of network identity. No automatic profile selection or credential replay.
- ConfirmedVoucherSave requires explicit save approval, unchanged selected network, gateway matching the chosen profile, valid original credentials and matching session result. HTTPS matching and legacy HTTP matching are distinct; HTTP requires separate acknowledgement of unauthenticated evidence. Failed, ambiguous, cancelled or existing-session login results cannot authorize saving.
- Vault rechecks persisted profile ID/name/gateway and deduplicates by profile, username and protocol; no silent eviction. Profile catalog and records share one authenticated atomic file. Low-level put remains for previous storage tests; UI must use confirmed-save path.
- This is the domain/storage subphase, not a wired UI. Next 07B2 must bind authorization to the actual login attempt, scope consent to that attempt, discard credentials on stop/network change/cancel and execute storage off main thread. Next 07C explicit listing/reuse/deletion. Device and field acceptance still required.

## Phase 07B2 — explicit profile UI and attempt-bound save
- Manual profile creation for the currently selected gateway, no automatic selection even when only one profile matches. Selection resets on network or catalog change. Names are user labels, not authenticated network identities.
- One-attempt opt-in to save original normalized credentials after the actual LoginAttemptController result; separate opt-in for legacy HTTP evidence. Reject wrong gateway, missing approval, failed/mismatched results, cancelled or disposed attempts. The vault rechecks the persisted profile. No automatic login.
- Serial storage worker; no disk or key generation on the Compose thread. On network change or Activity stop, clear catalog state and cancel queued work; a write that has already begun may finish atomically. Refresh catalog on start. Storage failure does not alter authentication result.
- 9 additional JVM tests for actual attempt-bound save and profile controller; device tests and saved-card UI/reuse/deletion remain 07C and field acceptance.

## Phase 07C — saved voucher selection and deletion
- Read a single encrypted catalog snapshot, expose only masked account, record UUID, profile UUID and protocol to presentation; do not expose raw credentials in lists. Existing v1 orphan records are not shown or adopted.
- Explicit selected profile on current gateway and current catalog object identity required for load/delete. No automatic selection based on gateway. Separate confirmation for loading and deleting. Load one record on serial worker with persisted profile check, fill masked form only, reset HTTP/save consent; no automatic login or network request. Clear form on network/profile change and before deleting.
- Delete only from local vault, not RouterOS. No cloud sync, no backup, no silent eviction. Current UI manages cards for manually selected profiles matching current gateway; offline catalog management and deleting/renaming profiles are not implemented.
- Cancel queued operations and ignore stale completion on lifecycle/network change; a write already started may complete. Decrypted credentials exist transiently in process memory; no forensic deletion guarantee.
- 7 added JVM tests for masked catalog, scope, explicit selection, stale callbacks, and deletion. Real AndroidKeyStore, Compose UI and device acceptance remain pending. No new libraries or permissions.

## Revision 2026-11-27 — maximum five saved vouchers
- User decision: maximum five new saved voucher records globally across all profiles, not five per profile. Profile limit remains 20. Existing card updates at capacity are allowed, new records rejected without eviction.
- Existing pre-limit vaults containing 6–20 records remain readable; the user must delete records explicitly before adding any new card. Deletion and existing updates remain possible. The UI displays total stored records including older orphan records. Orphans are not adopted automatically; explicit orphan recovery/deletion UI is still pending if any pre-release data exists.
- All confirmed-login, encryption, profile isolation and consent rules remain unchanged. Login without saving remains possible. Tests exercise global capacity, updates, and legacy oversized vault compatibility.

## Revision 2026-11-27 — per-network retention (supersedes global limit)
- Five cards per explicitly selected profile UUID, manual mode default, automatic oldest replacement opt-in persisted per profile. Mode change does not delete cards. Oldest means least recently successfully saved, using persisted ordering, not the device clock. A repeated username updates its existing record and moves it to newest even if protocol changes.
- New confirmed save in automatic mode evicts only the oldest necessary records of that profile in the same atomic encrypted write. Failed or cancelled authentication, stale mode authorization or failed atomic replacement must not evict cards. Manual mode rejects new records when full; manual deletion is always available.
- Vault document v3 stores mode; v1/v2 decode with manual default and preserve legacy excess. Up to 20 profiles with five each and bounded pre-release excess/orphans. No automatic profile adoption. Old versions cannot read v3; no downgrade support. Existing excess is preserved until explicit deletion or next successful new save after opting into automatic mode.


## Phase 12A — local-data hardening
- Apply Android FLAG_SECURE to the app window to limit ordinary screenshots, screen recording and recent-task previews, including login, gallery review and subscriber details. This is intentionally app-wide for the single-Activity UI; it may also prevent screenshots for support. Device/OEM behavior and accessibility remain to be checked; not a defense against compromised devices or external cameras.
- Redact VoucherInput.Result.toString() while preserving validation and exact returned value. Wipe the owned plaintext codec buffer and replaced backing arrays, bound growth before allocation; format v3 and AES-GCM unchanged. DataOutputStream, Strings, platform internals and GC copies may still retain sensitive data; no full memory-erasure guarantee.
- Legacy duplicate accounts within a profile are not silently overwritten or deleted on save. Require explicit deletion of duplicate before saving that account; other profiles unaffected. Existing five-card retention and atomic writes remain unchanged. Four regression tests added; hardware and device verification pending.
